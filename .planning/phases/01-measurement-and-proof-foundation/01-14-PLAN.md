## Long-run protocol (applies to plans 01-14, 01-15, 01-16)

- Claude submits jobs only through the MCP tools (`bench_baseline`, `bench_experiment`, `bench_resume`, `bench_shutdown`), per CONTEXT ("Claude only submits via MCP"). `curl` is used only for read-only GETs (`/api/status`, `/api/jobs/<id>`, `/api/funnel`), and shell commands only to start server processes. The jobs run on the owner's live bench server, unattended.
- The MCP server is loaded when the Claude Code session starts. These plans need the tools added in plans 01-08..01-13 (`bench_baseline` with lo/hi/lgen/replicate/gate, `bench_job`, `bench_funnel`, `bench_shutdown`); a session older than those plans must reconnect the MCP server (`/mcp`) or restart first.
- A job ID is recorded the moment it is returned, but a job is called **started** only after `GET /api/jobs/<id>` shows `"started": true` (first game row). Queued jobs are recorded as queued.
- No executor waits for hours. Each plan ends after submission; the next plan's first task carries a `<precondition>` that the jobs are done. If they are not, the executor stops and returns a blocking checkpoint naming the job IDs and the remaining time from `/api/status`; the owner resumes the phase when `.venv/bin/python -m bench.cli wait <id>` exits 0.
- During a server swap no MCP bench tool may be called while no server answers: the MCP server starts the main checkout's server on demand and would take the port. Once the replacement server answers on port 8765, MCP calls go to it.
- Plans 01-14..01-16 run in the main checkout (the live server, `.venv` and commit A live there); their checks call `.venv/bin/python` directly.
