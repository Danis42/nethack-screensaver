# Architecture Patterns: Development Method and Testing Architecture

**Domain:** Rule-based NetHack 5.0 bot (AutoAscend port) developed against a deterministic headless bench
**Researched:** 2026-11-12
**Scope:** Not the bot's runtime architecture. This is the architecture of the *method*: how progress is measured, tested, triaged, refactored and proven.
**Overall confidence:** MEDIUM-HIGH. Facts about the repo and the archived database are verified (HIGH, computed directly from `bench/`, `scripts/`, `nethack_screensaver/` and the archived 146,743-game `results.db`). Statistical designs are standard methods (MEDIUM-HIGH) but the specific parameters (discordance rates, clone correlation) must be measured in Phase A, not assumed.

---

## 0. Recommendation in one screen

1. **One decisive metric: the natural-game funnel.** Per-stage reach rates and conditional pass rates over natural, seeded, unstaged games, with Wilson intervals. Fix the definition first: today's `rung{n}` metrics are *not* a funnel (see F1).
2. **Two commit kinds, two gates.** *Refactor* commits must be bit-identical on a gate set of seeds (frame-hash chain). *Behavior* commits need a paired, pre-declared experiment: one primary funnel stage plus guardrails. Never mix them in a commit.
3. **Switch to lgen-seeded dungeons and a sequential e-process on discordant pairs.** `game.py` does not pass `lgen`, so every behavior change re-rolls all later dungeon levels. This destroys pairing for broad changes (F3). One flag fixes the largest source of noise; it needs one clean re-baseline.
4. **Late-stage tools produce *ability* evidence, never *funnel* evidence.** Every staged/scenario/rewind result goes into the same store under an evidence class and a job ID. Transfer is checked by a measured product: natural *supply* rate of the prerequisites x staged *ability* pass rate = predicted natural conversion, compared to actual when natural games get there.
5. **Failure triage is a pipeline, not a read-through.** Replay (sha, seed) to build a compact death dossier, extract deterministic features, label with a closed taxonomy (LLM offline, temperature 0, validated against hand labels), rank system-level tags by expected funnel gain.
6. **Refactor by system, on demand, under the gate.** Strangler-fig extraction in the order the roadmap needs each system. No big-bang rewrite. File-size and bare-except ratchets stop regrowth.
7. **Proof = job ID + full SHA + a query, generated by a command, not typed.** Trailers `Bench-Job: N` rendered from the DB and checked by a script. Starting a job returns only after the first game is stored.

### Data flow: the improvement loop

1. **Measure** `main`: funnel job at N=2304 dev seeds (91 min) -> `bench funnel main` -> stage table + stage x cause table.
2. **Triage**: for the worst stage, dossiers for all deaths there -> labeled by system tag -> ranked by expected gain (Section 5).
3. **Hypothesize at system level**: "survival.escape fails to leave via stairs when HP<40% and a monster is adjacent" - a statement about a system, with a predicted funnel effect and a named primary stage.
4. **Build behind a flag, off by default** (refactor first if the system is tangled; under the refactor gate). Gate passes with the flag off -> proves no side effects.
5. **Experiment**: job spec declares `{primary: stage_reach, guardrails: [...], flag: ..., max_n}`; e-process stops on evidence or at max N. Verdict stored on the job.
6. **Merge** with trailers `Bench-Job: N` (generated). If the target stage is late and nothing reaches it naturally: use Tier B/C for the ability, and add the *supply* rate to the funnel as a tracked stage-prerequisite.
7. **Re-baseline** `main` on the confirm range at phase boundaries (not every merge) - the independent check that dev-range wins were not seed-specific.

## 3. Natural-game funnel (the main metric)

### 3.1 Definition

- A game "reaches stage s" iff `s in game["ladder"]` (first-turn dict already recorded). **Never** use `game["rung"]`.
- Stages are an explicit ordered chain in code, with a documented rationale. Proposed chain, reach rates from baseline `72ca0b6` (n=2304, Wilson 95%):

| Stage | Detector source | Reach (baseline) | Notes |
|-------|-----------------|------------------|-------|
| start | all games | 100% | |
| Dlvl 3+ | `max_depth>=3` (or first-arrival snapshots) | 94.5% | early-wall refinement; not in `ladder.py` yet |
| Dlvl 5+ | `max_depth>=5` | 84.7% | |
| mines | `ladder.mines` | 58.3% (56.3-60.3) | NOT 76%; see F1 |
| minetown | `ladder.minetown` | 20.2% (18.6-21.9) | |
| sokoban | `ladder.sokoban` | 24.7% (23.0-26.5) | |
| sokoban_solved | `ladder.sokoban_solved` | **0/2304** | verify detector or solver (F2) |
| mines_end | `ladder.mines_end` | 11.1% (9.9-12.4) | |
| dlvl15 | `ladder.dlvl15` | 7.7% (6.7-8.8) | |
| quest (portal level) | `ladder.quest` | 5.2% (4.4-6.2) | |
| medusa | `ladder.medusa` | 1.1% (0.7-1.6) | |
| castle ... ascended | `ladder.*` | 0% | cannot be measured by natural games today |

- Two numbers per stage: **reach rate** P(stage) over all games (the primary, causally clean, paired-test-friendly quantity) and **conditional pass** P(stage | previous stage reached) (diagnostic). Do *not* use the conditional as the experiment's primary: conditioning on a post-treatment variable biases the paired comparison (the two sides' reached-sets differ).
- Output per stage also: median turn of arrival, and an **exit table**: of games whose *last* stage was s, counts by cause class (killed by X / starved / stuck / crashed / aborted). This is the Pareto that feeds triage (F11 is its baseline).
- The chain is plan-aware: pilgrim route today; if the plan changes (e.g., skipping Mines' End), the chain table changes with an explicit version string stored in every funnel report.
- Add a `funnel_version` and compute it from `autoascend/ladder.py` + `bench/funnel.py` so archived reports remain interpretable.

### 3.2 Power analysis: how many games to detect an improvement

Paired design, McNemar-style, two-sided alpha=0.05, power 0.80:

    n  =  (1.96 + 0.84)^2 * q / d^2  =  7.85 * q / d^2          (q = discordant share, d = true diff in reach rate)
    MDE80 (minimum detectable diff at n)  ~=  2.8 * sqrt(q / n)

Independent design (no pairing): n per side = 7.85 * (p1(1-p1) + p2(1-p2)) / d^2.

q must be *measured per change class* (Phase A pilot), but archived data gives ranges (metric `dlvl6`, 54 experiments, n=2304 paired):

| q regime (measured in archive) | q | MDE80 at n=576 | n=1152 | n=2304 |
|--------------------------------|---|-----------------|--------|--------|
| narrow fix (median) | 0.048 | 2.6 pp | 1.8 pp | 1.3 pp |
| typical (p75) | 0.255 | 5.9 pp | 4.2 pp | 3.0 pp |
| broad change (max ~ independent) | 0.465 | 8.0 pp | 5.6 pp | 4.0 pp |

Worked sample sizes (all assumptions explicit; times at 25 games/min for the candidate side only):

| Question | d | q assumed | n pairs | Time (candidate side) |
|----------|---|-----------|---------|------------------------|
| Early-wall system fix moves `Dlvl5+` 84.7% -> 88% | +3.3 pp | 0.25 | ~1800 | ~72 min |
| Food system halves starvation 14.5% -> 7.5% (metric `starved`) | -7 pp | 0.10 (tuned to affected subset) | ~160 | ~7 min |
| Escape system moves `mines` reach 58% -> 63% | +5 pp | 0.25 | ~785 | ~31 min |
| `minetown` reach 20% -> 25% | +5 pp | 0.20 | ~630 | ~25 min |
| Late: `medusa` reach 1.1% -> 2.2% | +1.1 pp | 0.02 | ~1300 | ~52 min |
| Late: `medusa` same, independent design | +1.1 pp | - | ~2100 per side | ~84 min x 2 |
| Anything at `castle`+ (baseline 0%) | - | - | not measurable by natural games | use Tier B/C |

Takeaways:
- **Early-wall work is cheap to measure** (hundreds of games, tens of minutes). It is *not* the statistics that stalled the last session; the 20-seed staged runs ("7/20 vs 8/20") had MDE of ~35 pp.
- **Late stages cannot be powered naturally** until the funnel moves. A reach rate near 1% needs ~1000+ games per effect of +1 pp. The funnel's job at that depth is *tracking*, not deciding.
- Rare-stage conditional rates have tiny denominators (25 games reached `medusa`: conditional 14.1%, CI 9.8-20.0% on the 177 that reached `dlvl15` -> medusa). Report them with their denominator and never compare them across commits without the Tier-B method.

### 3.3 Sequential testing and early stopping

Current: Wald interval at 5 checkpoints (`z=2.576` early, `1.96` final). Problems: Wald fails when n10+n01 is small; checkpoints only; cannot express non-inferiority.

Recommended (all computed on *discordant pairs*, which is where McNemar's information lives):

1. **Verdict "better/worse": always-valid sign e-process.** Under H0 (no change in reach rate), conditional on a pair being discordant, P(candidate is the one that reached) = 0.5. Mix over theta ~ Beta(a,b) (a=b=1, or a=b=0.5): `E_t = 2^(n10+n01) * B(a+n10, b+n01) / B(a,b)` (use `scipy.special.betaln`). Reject H0 when `E_t >= 1/alpha` (alpha=0.05; Ville's inequality makes this valid under *continuous monitoring and optional stopping*). Check after every stored pair; no checkpoints needed. Runs in 10 lines. This replaces `judge_paired`'s verdict logic; keep checkpoint intervals only as displayed effect sizes.
2. **Effect size and interval at stop:** Newcombe/Tango score interval for paired proportions (or exact conditional binomial on discordants). Report the interval *with the bias warning* that estimates at an early stop overstate effects; the e-process verdict is what's controlled, the interval is descriptive. For final claims, require the **confirm-range replication** (Section 3.4).
3. **Guardrails (no-harm):** each experiment lists guardrails (e.g. `died` non-inferior by 2 pp, `crashed`, `hung`, `dlvl5`, and the funnel stage immediately upstream of the primary). Use a betting-based confidence sequence for the mean of the paired difference D_i in {-1,0,1} (Waudby-Smith and Ramdas; applies to bounded data) and require the lower bound > -margin before merge. Non-inferiority needs half-width < margin: n ~ 3.84 q / margin^2 (e.g. 2 pp margin, q=0.05 -> ~480; q=0.25 -> ~2400).
4. **Futility stop:** if the e-process for the *reverse* hypothesis with the planned-MDE alternative crosses 1/alpha or the MDE at current n exceeds the claimed effect by 2x at max N, stop and record "no measurable difference at MDE X" (as the existing `Verdict.detectable` already does).
5. **Validate the engine before trusting it:** (a) simulation: type-I error under optional stopping with q in {0.01, 0.05, 0.25}; (b) **A/A using the archive**: random sign-flips of paired outcomes from the 62 real experiments must reject <=5% of the time; (c) power curves vs the formula above. Make this a unit test in `tests/test_bench_stats.py`.

Confidence: MEDIUM-HIGH. The conditioning argument and the Beta-mixture e-value are standard (always-valid / Ville-inequality tests; see Sources); the specific shortcut of running it on discordant pairs only is mine and must be validated by (5) before use.

| Measure | Effect | Cost |
|---------|--------|------|

## 4. Late-stage testing: how to use rewinds, stages, scenarios legitimately

### 4.1 Evidence classes (the rule that prevents "castle 8/20")

| Class | Tool | May support | May NOT support |
|-------|------|-------------|-----------------|
| **N** natural | bench natural games (`games` table) | any progress claim, funnel rates | - |
| **B** natural-prefix | arrival bank: natural game up to stage entry, fresh dice afterward | conditional stage pass rate, ability fix at a stage entered naturally | claims about earlier stages |
| **S** staged | `staging.py` stages with a *measured* kit | "ability A works given kit K" | any funnel rate; "bot reaches X" |
| **C** scenario | `scenario_lib.py` situations with checks | regression of a single behavior | anything quantitative about play |
| **R** rewind | `rewind.py` infinite lives | diagnosing death depth-of-cause; ceiling analysis | any claim of ascension; funnel rates |

Hard rule enforced in code: the funnel query reads `games` only; classes S/C/R are written to `tool_games(evidence_class, stage, scenario, job_id, sha, seed, result_json, kit_json)`. A report that mixes classes refuses to render a rate.

### 4.2 Ability contracts: making late abilities testable on their own

For each late stage define a contract (a data record next to the stage code, e.g. `autoascend/systems/stages/<stage>.py`):

```
Stage "medusa":
  needs:        [levitation_source OR digging+dry_square, reflection OR blindfold+telepathy, XL>=?, HP>=?, AC<=?]
  procedure:    cross -> reach downstairs -> kill/avoid Medusa
  pass check:   max_depth > start_depth AND not drowned AND not stoned
  events:       medusa_levitate, medusa_landed, medusa_no_levitation ...   (StatsLogger already has these)
  scenarios:    medusa-dig, medusa-levitate (already in scenario_lib.py)
```

Two measured quantities per contract:
- **Ability rate** `p_ability` = pass rate in staged/scenario runs given the contract's `needs` (Tier C).
- **Supply rate** `s` = P(natural game arrives at the stage satisfying `needs`). Measured from the natural funnel via `snapshots` (first-arrival-at-rung snapshot already records gear, inventory, XL, HP, AC) - a new `needs_met` check over the stage-arrival snapshot, no bot change.

Predicted natural conversion at the stage = `s * p_ability`. Track predicted vs actual (`transfer ratio`) once enough natural arrivals exist. This turns "staged 13/20" into two honest numbers: "ability 65% given kit; kit exists in X% of arrivals".

Supply is itself a product (the bot must *acquire* levitation, reflection, armor), so many "late walls" are early/mid acquisition systems (resources). That is the architectural reason the funnel has *prerequisite stages* (kit milestones) in addition to location stages.

### 4.3 Kit realism: staged starts that cannot lie

Today `Stage` kits are hand-chosen (`MIDGAME_KIT`, `MEDUSA_ARMOUR`, human 5.0 ascender statistics from 199 dumplogs). That is a *ceiling* kit, not a natural one. Fix:
1. **Kit sampler**: stages draw kits from (a) the empirical distribution of *natural arrival snapshots* (as they appear) and (b) a "target" distribution from reference ascensions (`reference_games`, `dumplog`). Run S-class tests under both: natural-kit pass rate is the transfer-honest number; target-kit pass rate is the ability number.
2. **Realism check** (automated, runs in `staging` tests and at every stage run): compare the staged hero's start state to natural arrivals - XL, HP/HPmax, AC, hunger, prayer timeout, Luck, pet present, turn counter, inventory classes. Wizard-mode artifacts already known: prayer timeout (`staged prayer timeout fix` in git log), luck/force-god prompts (`WIZARD_PROMPTS`), pet absence, full HP. Report standardized differences; flag any stage whose key parameters are outside natural p10-p90.
3. **Arrival state stress**: stage with partial HP, hunger "Hungry", prayer timeout unspent-or-not, as discrete variants. A stage that only passes at full HP/safe prayer is not natural.

### 4.4 Tier B: the arrival bank (natural prefix + resampled dice)

Idea (fixed-effort splitting from rare-event simulation, mechanically the same trick as `scripts/rewind.py`): run a seeded natural game to the first turn it reaches stage s; from that state, produce M clones with different dice and measure what share pass stage s. The prefix is natural, so the arrival state (kit, HP, hunger, prayer, level knowledge) is real by construction. The reseed mechanism already exists and is verified exact (`rewind.py`: "A replay is exact", `set_current_seeds(nh, new, new, False, 0)`).

Two implementations:
1. **Replay-based (use now):** regenerate state by replaying (seed, bot sha) to the arrival turn with a reseed at the arrival turn (as rewind does). Cost = a full prefix per clone. With ~25 Medusa arrivals per 2304 games and prefix times of minutes, clones are affordable offline; cluster correlation is the issue.
2. **Fork-at-arrival (spike, unverified):** `os.fork()` a worker at the first frame of stage entry so the child inherits the entire NetHack state; children continue with fresh dice and/or a different flag set. Would make Tier B nearly free. **Unverified whether NLE's embedded game survives fork** (LOW confidence; 1-day spike, abandon if it does not).

Statistics: clones from one arrival are correlated. Use arrivals as clusters (cluster bootstrap or logistic with cluster-robust SE). Effective sample is between the number of arrivals and arrivals x M; estimate the intra-class correlation rho from pilot data; design effect 1+(M-1)*rho. Report "N arrivals, M clones each, ICC rho" with every Tier-B rate.

A Tier-B result for a change that is gated to be inactive before the stage (flag keyed on dungeon/level) is *also* a valid natural paired comparison: the two commits play identical prefixes by construction (the gate in Section 6 proves it), so only seeds that reach the stage can differ. That is the cheapest honest late-stage experiment: run baseline once (stored), run candidate on the same seeds, discordant pairs are exactly the stage arrivals. Needs N large (1000s) - Tier B multiplies the effective sample.

### 4.5 Validating that staged/scenario work transfers

Protocol per ability, in order:
1. **Contract written** (needs, check, events).
2. **S-class pass rate** with CI, N>=40 paired seeds (CI half-width ~15 pp at p=0.5; enough to detect a jump from ~10% to ~60%, not 8/20 vs 7/20). State the MDE in the report.
3. **Realism report** for the stage (4.3). Failing realism = no claim.
4. **Supply rate** from natural snapshots (4.2) - if supply is ~0, the ability is irrelevant until an acquisition system exists; schedule that system first.
5. **Tier-B or natural measurement** when arrivals exist; compare to prediction; record the transfer ratio. A ratio far from 1 downgrades the staged evidence for that stage and triggers a stage-definition fix.
6. **Regression**: the scenario suite (`scenario_run.py all`, exit code 0/1) joins the pre-merge checks for any commit touching the stage's system. Each scenario also records *how often natural play triggers it* (event counters) so unreachable scenarios do not accumulate.

Hard ban: any claim of the form "reaches X" cites class N or B only. "Works at X" cites S/C and names the contract.

### 4.6 Rewinds and staging as development tools, specifically

- `rewind.py` for **triage depth classification** (Section 5) and ceiling analysis, never for pass-rate claims. Its output joins `tool_games` with `evidence_class='R'`.
- `staged_run.py` and `scenario_run.py` get a unified runner that registers a job (`kind='tool'`), plays seeds in parallel through the existing `ProcessWorker`-like pool, and writes rows to `tool_games`. `scenario_run.py` currently shells out per game with PYTHON path from `SCREENS_BENCH_PYTHON` (hard-coded default under `~/.cache/screens-nh5/venv`); fold that into bench config.
- Remove `SCENARIO_HOOK` `exec()` from the regular path (arbitrary code from env, CONCERNS.md).

## 5. Automated failure triage

### 5.1 Pipeline

```
 stored games (natural, from funnel jobs)
        │  select: ended in death / starve / stuck / abort, stage = k
        ▼
 [1] DOSSIER BY REPLAY   replay (sha, seed) with a tracer; keep last 300 turns + milestones
        ▼
 [2] DETERMINISTIC FEATURES   (cheap, reproducible, no LLM)
        ▼
 [3] CLUSTER + LABEL          closed taxonomy; LLM offline; hand-validated
        ▼
 [4] RANK                     expected funnel gain per system tag
        ▼
 [5] OPTIONAL DEPTH-OF-CAUSE  rewind-distance probe: how far back must we go to survive?
```

**[1] Dossier by replay.** Games are deterministic per (sha, seed, lgen mode, env fingerprint), so a dossier is regenerated on demand instead of recording everything for 100k games (F10). A tracer observer (like `_DeathContext`, observation-only so the game is unchanged) records per step: turn, HP/HPmax, hunger, depth/level, position, message line, **chosen action and the decision source** (strategy layer name from the arbiter, Section 6.3), visible hostile monsters (name, distance), prayer availability, Elbereth state, escape items in inventory. Output: JSON of ~300 turns before the end + a per-level timeline (first arrival turn, XL, HP) + last inventory. Requires the decision-source tag, which is a small hook in the strategy dispatch (do it as the first commit under the gate).

**[2] Deterministic features** (the part to trust most): killer class, stage, XL vs depth (danger ratio), HP trajectory shape (sudden drop vs attrition), min HP fraction over the last 50 turns, turns since last progress (stuck), hunger state at death and turns hungry, prayer used / available / safe, escape resources present and unused (scroll of teleport, wand of digging, stairs distance), whether it fought or fled, Elbereth attempted, `rewind` depth label (Section 5.5). These alone give a usable Pareto.

**[3] Labeling.** Closed two-level taxonomy, system-oriented (v0, to be revised by the first open-coding pass):

| System | Tags |
|--------|------|
| survival.escape | `no_flee_attempted`, `fled_wrong_way`, `stairs_unused`, `elbereth_ignored_monster`, `escape_item_unused`, `engulfed` |
| survival.hp | `healing_unused`, `prayer_unused`, `prayer_unsafe`, `low_hp_exploration` |
| survival.combat | `engaged_too_strong`, `wrong_weapon`, `passive_monster` (eye, jelly, acid blob), `ranged_unwarned` (wand/ray/breath) |
| food | `no_food_acquired`, `ate_dangerous`, `corpse_old`, `prayer_for_hunger_unused`, `weak_not_responding` |
| resources | `armor_not_worn`, `item_misused`, `cursed_item`, `unidentified_gamble` |
| navigation | `stuck_level`, `trap`, `boulder`, `door_loop`, `shop_trouble` |
| stage.* | `sokoban_fail`, `mines_end_wait`, `medusa_cross_fail`, `castle_*`... |
| other | `bot_exception`, `watchdog`, `bad_luck_unavoidable` |

Process (follows published practice, see Sources): (i) **open coding**: LLM writes a free-text "first clearly wrong step" and root cause per dossier for a sample of ~150 deaths; (ii) cluster the texts (embeddings + HDBSCAN, or LLM-reconciled merge across several rephrased clustering prompts) and have the owner review into the closed taxonomy with inclusion/exclusion notes; (iii) **closed coding** of all dossiers with the fixed tags, JSON output, temperature 0, prompt includes taxonomy, the deterministic features, and a curated rulebook excerpt from `.planning/research/*-NH5.md` (SURVIVAL, FOOD, PRAYER). Published results show taxonomy and failure-location guidance raise root-cause accuracy substantially (the taxonomy-only and location-supplied conditions in the agent-workflow study), so supply both: the taxonomy, and the **decision-step location** from the tracer.

**Controls on the LLM** (it is an analyst, never part of pass/fail):
- Store `model_id`, `prompt_hash`, temperature, taxonomy version per label; labels are append-only rows in a `triage` table keyed by (sha, seed, prompt_hash).
- **Validation set:** the owner hand-labels ~30 dossiers once; report agreement (Cohen's kappa) per tag group; tags with kappa < 0.5 are not used for prioritization.
- Treat LLM output as untrusted text (CONCERNS.md already warns about the Ollama sweep); never feed it into `autoascend/` data files.
- Local Ollama (as `fixes_triage.py`) for volume; Claude for the open-coding pass and for the "write the hypothesis" step. Cost scales with dossier size (~300 turns x compact lines): keep dossiers under ~6k tokens.

**[4] Ranking by expected gain.** For tag T at stage k with `d(T,k)` games ending there out of `r_k` games that reached k, and conditional pass `c_k` to the next stage:

    gain(T,k) ~= (d(T,k) / N) * (continuation probability after surviving)  ~  d(T,k)/N * c_next(k)

i.e. "how much of the stage-k attrition does fixing T plausibly reclaim". Sort descending; fix systems, not tags: sum gains per system across stages. This is what replaces "a monster per session". Count the same tag at multiple stages as one system fix with one experiment, primary metric = the reach rate of the stage with the largest gain, guardrail = adjacent stages.

**[5] Depth of cause via rewind (optional, high value).** The REWIND-20 study: of 182 deaths, 68% were saved by a reroll 100 turns back (tactical close calls), 16% needed 1000 back, 9% needed 5000 back, 8% never; 12 of 16 5000-back deaths involved hunger. Automate `rewind_depth` as a dossier feature for the worst stage's deaths (cost ~5-15 replays per death, offline). It classifies tactical (survival.escape/combat) vs strategic (food, armor, resources) causes without LLM judgment and cross-checks the LLM tags.

### 5.2 What triage must produce for the roadmap

Per cycle: a table `system | stage | n deaths | expected gain | rewind depth mix | example dossier IDs`, regenerated by one command, with every row backed by a query (`WHERE job_id=... AND tag=...`). The first cycle on the fresh baseline decides the order of the early-wall phases (food, escape/HP, stuck, resources) with evidence, replacing the guesses in PROJECT.md.

## 6. Refactoring `agent.py` and `global_logic.py` safely

### 6.1 Two commit kinds

| Kind | Rule | Gate |
|------|------|------|
| `Kind: refactor` | No behavior change allowed. Moves code verbatim, renames, splits. | **Bit-identical trace** on the gate set |
| `Kind: behavior` | Intentional change, flag-guarded, one system per commit | Paired experiment with declared primary + guardrails |

A commit that does both is rejected by `check_claims.py` (message trailer is required; a diff stat heuristic warns on large behavior-looking refactors). The trailer is the only extra bookkeeping.

### 6.2 The deterministic regression gate

- **Trace**: during `run_game`, an observer maintains a rolling SHA-1 over each frame's `tty_chars` and `blstats` (exactly what `tests/test_replay.py` already hashes) and records `[turn, digest]` every 250 turns, plus the final digest, into `GameResult.trace`. Observation-only, so the game is unchanged (same design as `_DeathContext` and `snapshots.Recorder`).
- **Gate set**: 200 dev seeds (about 8 min at 25 games/min on the candidate side; baseline stored) plus 8 *long* seeds known to reach Dlvl 15+ and 8 that exercise Sokoban/Castle/Medusa code paths (selected from baseline `ladder` data). Job kind `gate` compares `trace` lists; on mismatch it reports the first divergent (seed, turn window), which localizes the offending refactor. Exempt only `watchdog` endings (load-dependent; `replay_check.py --skip-end watchdog` precedent).
- **Quick local gate** (`scripts/gate_quick.py`): 20 seeds truncated at 3000 turns (`max_steps`), runs in ~1-2 min for the inner loop; the full gate runs before merge.
- **Determinism hazards to pin before refactoring** (these cause false gate failures or hidden behavior changes): iteration order of sets/dicts (PYTHONHASHSEED=0 is set by the runner and `replay_check` relies on it), the order of `random`/numpy RNG calls inside the agent (`Agent(seed=0)`), `numba` JIT numerics, floating-point reductions, time-dependent paths (`fixed_clock` shim). A refactor that reorders RNG draws is a *behavior* change; the gate will say so.
- Add the gate to the pre-merge checklist (no CI exists, CONCERNS.md): `scripts/premerge.sh` runs `pytest`, `gate_quick`, claim check; the full gate and any experiment are jobs whose IDs go in the trailer.

### 6.3 Characterization tests for the god objects

Full-game traces characterize *behavior*; add decision-level tables for the code being extracted:
1. **Decision capture**: with the tracer, dump at selected moments a small *decision context* (blstats, adjacent/visible monsters, inventory summary, level flags) and the chosen action + source. Store ~50 per target function (`emergency_strategy`, `fight2`, `_stair_escape_due`, `eat_from_inventory`) as JSON fixtures in `tests/data/decisions/`.
2. **Pure cores first**: extract the decision as a pure function of plain values (the pattern already used by `prayer_trouble(blstats, safe_hp, safe_hunger, has_food)`, `hunger_prayer_gap`, `closed_shop`, `storeroom_chests` at the top of `agent.py`, and by `prayer.py`, `castle.py`, `digging.py`). Table-driven tests replay the fixtures against it. Keep the generator "shell" thin.
3. **Gate for the shell**: the trace gate proves the glue.

### 6.4 Target module boundaries (systems, strangler-fig, no big bang)

Boundaries follow the roadmap's systems. Dependency rule: perception -> state; systems -> state + effectors; stages -> systems; **nothing imports `agent`**; each module declares a narrow `typing.Protocol` for the context it needs (so tests use `SimpleNamespace`/`tests/fake_player.py`, the project's existing style, not a full Agent).

```
autoascend/
  agent.py              # shell: wiring, update loop, exception handling (target < 600 lines)
  perception/           # get_message_and_popup, update/update_state, update_level, terrain, items/shops/corpses (agent.py ~397-800); monster_tracker/, glyph/
  effectors.py          # the ONLY code that sends keys: move, melee, pray, eat, engrave, zap, fire, cast, dig_down, kick, search (agent.py ~835-1135)
  nav/                  # bfs/path/go_to (agent.py 1193-1360), exploration_logic.py, stuck.py, boulders.py
  arbiter.py            # explicit ordered reflex layers replacing the nested .preempt(...) chain in GlobalLogic.global_strategy (global_logic.py ~1310-1362)
  systems/
    survival/           # fight2, _stair_escape*, emergency_strategy, prayer.py, elbereth, healing (agent.py 1361-1620, 1855-1990)
    food/               # hunger, eat_from_inventory, eat_corpses_from_ground, eat_eye_corpse, cure_disease, unicorn horn (agent.py 1622-2079 subset)
    resources/          # item/ (inventory, priority, wishes, scrolls, accessories), shop selling, altar identify, excalibur (global_logic 984-1140)
    stages/             # one module per stage; each exports a StageAbility (contract in 4.2): sokoban (global_logic 747-960, soko_solver/), mines/minetown, quest_portal, medusa (_cross_medusa 349-412), castle (412-543), gehennom...
  plans.py, ladder.py   # unchanged data
```

**The arbiter** is the highest-leverage structural change. `global_strategy()` is currently ~50 lines of chained `.preempt(...)`: an implicit priority stack whose order is only discoverable by reading the chain. Make it an ordered list `[(name, trigger, strategy)]`: (a) unit-testable ordering (e.g. "emergency outranks eat outranks explore"), (b) each action is attributed to a layer name for the tracer (Section 5), (c) layers can be toggled by flag for ablations. This is Brooks-style subsumption expressed in the existing generator `Strategy` objects (`autoascend/strategy.py`), so it is an incremental rewrite of one function, gated.

**Extraction order (demand-driven):**
1. Under the gate: add trace (6.2) and decision-source tag (5.1) - the first two commits.
2. Pure functions already at the top of `agent.py` (lines 36-131) into their systems.
3. The system the *next roadmap phase will change* (probably `survival` + `food`: `emergency_strategy`, `fight2`, `_stair_escape`, eating): extract verbatim, one system per commit, gate each.
4. Then `nav` (BFS/path/go_to: also fixes the diagonal-through-inwalkable bug in a *separate behavior commit*, never during the move).
5. `stages/` as each late stage is developed (the move of `_cross_medusa`, `_pass_castle` happens when Medusa/Castle work starts).
Rule: "touch it, extract it first". A system untouched by the roadmap stays where it is.

**Ratchets (cheap, mechanical, in `tests/test_structure.py`):**
- Max lines per module with an allowlist of current offenders at their current sizes (agent.py 2142, global_logic.py 1362, inventory.py ~1800). The allowlist can only shrink.
- No new bare `except:` / `pass` swallowing in `autoascend/` (counts ratchet down; CONCERNS.md lists the existing sites).
- No `import autoascend.agent` from any module under `systems/`, `nav/`, `perception/` (grep test).
- `Kind:` trailer present on every commit touching `autoascend/`.

## 7. Proof and traceability

### 7.1 What a claim is

`claim = (job_id, full_sha, query)`. Each progress statement in a commit message or summary is rendered by a command from the DB:

    $ uv run screens-bench claim 123
    Bench-Job: 123
    Candidate: 9f3a...  (40 hex)    Baseline: 72ca...
    Seeds: dev 0-1151, lgen=on, fingerprint=ab12
    Primary: reach(mines) +5.2 pp  [+2.9, +7.4]  e-process stopped at n=864 pairs
    Guardrails: died ok (lb -0.8 pp > -2.0), crashed ok, hung ok
    Query: SELECT ... WHERE job_id=123 ...

### 7.2 Mechanics

- **Job spec fields to add** (all inside the existing `jobs.spec` JSON): resolved full SHAs for both sides (already resolved in `start_experiment`), `seed_base`, `lgen`, `flags`, `primary`, `guardrails`, `funnel_version`, env fingerprint (NLE build commit `cb9d6572f` or current, python, numpy, numba, scipy versions, fixed_clock source hash).
- **Start confirmation (fixes "claimed to have started, was idle"):** `start_experiment` / `bench_baseline` MCP tools return `confirmed: true` only after at least one game row exists with `job_id = new job` (`SELECT COUNT(*) FROM games WHERE job_id=?`; `Scheduler._collect` already writes `job_id`). Otherwise return `confirmed: false, last_error: scheduler.error`. Add `bench liveness` (games in last 5 minutes, slots busy) to the status output. `games.job_id` is attributed to the *first* job that played the game; stored games are reused across jobs, so count by `(sha, seed range)` for coverage and by `job_id` for liveness.
- **Trailers**: `Bench-Job: 123` and `Kind: behavior|refactor|docs` appended by `scripts/trailer.py <job>` (renders from DB; owner/assistant never types numbers). `scripts/check_claims.py` verifies: job exists; `state='done'`; candidate SHA equals the merged tip or is the tree-identical parent (`git diff --stat <candidate>..HEAD -- autoascend nethack_screensaver` empty); verdict string in the commit message matches the stored verdict; a `Kind: behavior` commit has a done experiment, a `Kind: refactor` commit has a done gate job.
- **Tool runs get IDs too** (F8): `tool_games` rows carry `job_id`; commit messages say "ability pass 14/40 (S, job 131)" not "8/20".
- **Reports are generated**: `bench report --funnel main > docs/…` is regenerated, not edited; reports include sha, job ids, funnel_version, fingerprint. Minimal prose bookkeeping, matching PROJECT.md's "progress lives in the bench and git".
- **Final ascension record**: a `bench ascension <sha> <seed>` replay command re-plays the game from seed in a fresh process, asserts the end state, stores dumplog + frame-hash trace + the funnel context, so the clean ascension is reproducible from the seed (PROJECT.md active requirement). Natural, `lgen` recorded, no rewind, no stage: asserted from the job record (`evidence_class='N'`).

### 7.3 Things the bench already does well (keep)

- `PYTHONPATH` = commit worktree, `bench/worker.py` standard-library only so old commits play; full SHAs; stored games reused across jobs; job `result` JSON includes per-checkpoint verdicts; MCP wraps the HTTP API; `Store.interrupt_unfinished` after crashes. Do not rebuild; extend.

## 8. Patterns to follow

### Pattern 1: Observation-only recorders
**What:** Measurement hooks read observations and never act (`_DeathContext`, `snapshots.Recorder`, ladder `observe`). The trace, tracer and kit-realism snapshots follow suit.
**When:** every new measurement.
**Why:** A seeded game must play identically with or without it; the gate proves it.

### Pattern 2: Pure decision cores, thin generator shells
**What:** `prayer_trouble(blstats, ...)`-style functions that take plain values; the Strategy generator only collects the values and executes the action.
**When:** every extraction from `agent.py` / `global_logic.py`.

### Pattern 3: Pre-declared experiments
**What:** `{primary stage, guardrails, flag, max N, seed range}` in the job spec before any games are played.
**Why:** removes choosing the metric after seeing results; the e-process makes stopping honest.

### Pattern 4: Flag-guarded behavior, off by default
**What:** New behavior behind `AGENT_ARGS`/`SCREENS_FLAGS`; the commit lands flag-off (gate-clean), the experiment flips the flag on the same SHA.
**Why:** isolates the effect from code-motion noise, enables multiple variants from one SHA.

### Pattern 5: Evidence classes in the schema
**What:** The type system of the store enforces which tool may support which claim (Section 4.1).

---

## 9. Anti-patterns to avoid

### Anti-Pattern 1: Per-monster fixes judged on 20 seeds
**Why bad:** MDE at n=20 is ~35-45 pp; the "7/20 vs 8/20" results were noise; fixes accumulate mess.
**Instead:** system-level hypotheses from the triage Pareto, powered experiments, guardrails.

### Anti-Pattern 2: `rung>=n` as the funnel
**Why bad:** not a chain (F1); conflates skipping with passing.
**Instead:** `key in ladder` along an explicit chain.

### Anti-Pattern 3: Reusing the same seeds for every experiment forever
**Instead:** dev/confirm ranges; confirm touched at phase gates only.

### Anti-Pattern 4: Mixing refactor and behavior in a commit
**Instead:** `Kind:` trailer and the two gates.

### Anti-Pattern 5: An LLM in the pass/fail path
**Why bad:** non-deterministic, costly, breaks A/A comparability (PROJECT.md constraint).
**Instead:** offline analyst only; labels are data with provenance. An in-game planner is a separate research decision, to be measured as its own commit with its own determinism plan.

### Anti-Pattern 6: Staged pass rates as progress
**Instead:** evidence classes; supply x ability prediction; transfer ratio.

### Anti-Pattern 7: Hand-typed numbers in commit messages and summaries
**Instead:** `trailer.py` / `bench claim` render them from the DB.
